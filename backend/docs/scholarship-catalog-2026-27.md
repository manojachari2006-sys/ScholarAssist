## Data refresh procedure

The catalog is seed data managed by Flyway, not by hard-coded frontend cards. Flyway V11–V14 apply the reviewed corrections to existing installations. They scope updates by exact scholarship name/provider, add missing SDEF rules idempotently, and do not delete records. The same corrections are available as the explicitly runnable `scripts/refresh-scholarships-2026-27.sql` for a development database. Review the `WHERE` clauses and back up the database before running the script in MySQL Workbench. Running it again will not duplicate rules.

For a later academic year, first verify the provider's new call, deadline, rules and application destination; prepare a new additive Flyway migration and a matching refresh script. Do not edit an already-applied V1–V11 migration, delete old scholarships with application history, or overwrite user/application data. Mark only expired catalog offers inactive after review. Recheck via `GET /api/scholarships/search` and each `GET /api/scholarships/{id}/rules` response after migration.

## Eligibility labels

The scholarship detail quick check is **preliminary**: it compares the student's self-reported answers with the stored published criteria and does not persist or verify those answers. Any award is decided by the provider. The separate verified eligibility result uses only facts a reviewer explicitly confirmed from a specific verified document. A document's VERIFIED status alone does not establish any student fact. Conditions that cannot be expressed safely with the current facts remain manual questions and cannot be mistaken for reviewer-confirmed values.
